02

왜 이 프로젝트를 만들었는가

"사업 동향을 파악하려면 뉴스, 경쟁사 발표, 주가, 기술 논문을 매번 따로 찾아 정리해야 한다."
이 반복 작업을 LLM이 판단하고 Tool이 실행하는 에이전트로 직접 만들어 보고 싶었습니다.

출발 아이디어

사업팀장 관점에서 경쟁사(Sony, OmniVision, 중국 업체)·고객사·기술·응용처·시장 동향을 한 번의 요청으로 모아 보고서로 받아보기

시험해 보고 싶었던 것

하나의 요청이 사용자 입력 → Tool 실행 → 실제 데이터 → 업무 결과물까지 끊기지 않고 이어지는 에이전트 루프

수업 내용의 활용

Tool Calling, MCP 서버 구성, 에이전트 루프 설계를 실제 공개 데이터(뉴스 RSS, Yahoo Finance, arXiv)에 적용

데이터 조건

외부 교육장 프로젝트라 사내 데이터 대신 키 없이 쓸 수 있는 공개 데이터만 사용하고, 모은 데이터는 DB에 누적

06

설계 판단

① LLM이 판단할 것과 Tool이 정확히 처리할 것을 나눴다

LLM (gpt-5.5)

  • 무엇을, 어떤 언어로 검색할지
  • 어떤 기사의 원문을 읽을지
  • 기사의 중요도와 삼성 관점의 논조 판단
  • 비교·시사점·Action item 작성

Tool (Python 코드)

  • RSS·API 호출과 날짜 필터·중복 제거
  • 기업 태그 부여 (별칭 사전)
  • 주가 등락률 계산 (1주·기간)
  • DB 저장과 조회, 주 단위 언급량 집계

숫자 계산과 저장은 코드가 정확하게 처리하고, LLM은 판단과 글쓰기에 집중하게 했습니다. 시스템 프롬프트에는 "도구나 원문에서 확인한 수치만 쓰고, 출처를 밝힐 것"을 명시했습니다.

② 도구를 MCP 서버로 분리했다

도구를 앱 내부 함수가 아니라 MCP 서버로 만들어, 공개 MCP 서버(mcp-fetch-server)와 같은 방식으로 연결했습니다. config/mcp_servers.json에 서버를 추가하면 에이전트가 도구를 자동으로 인식합니다. 같은 서버를 LLM 없이 직접 호출하는 "데이터 수집" 배치도 만들어, 정기 수집은 비용 없이 돌아갑니다.

07

만들면서 확인한 점

모델 교체는 API 방식까지 바뀐다

처음에는 Claude API로 만들었다가 OpenAI로 전환했습니다. gpt-5.5는 Chat Completions에서 도구와 reasoning을 함께 쓰면 400 오류("Function tools with reasoning_effort are not supported")가 나서 Responses API로 다시 작성했습니다.

→ 에이전트 루프만 바꾸고 MCP 서버·DB·보고서는 그대로 재사용

검색 결과에 관련 없는 기사가 섞인다

"Sony image sensor" 검색에 "best Sony cameras to buy" 같은 카메라 쇼핑 기사가 들어왔습니다.

→ 제목에 센서 관련 키워드가 있는 기사만 남기도록 필터를 좁힘

원문 조회는 자주 실패한다

첫 실행에서 도구 오류 17건: 모델이 추측한 URL(404)이나 차단된 사이트 때문이었습니다. Google News 링크는 리다이렉트라 원문을 바로 읽을 수 없어, 원문 URL을 주는 Bing 결과를 함께 쓰도록 했습니다.

→ 오류는 결과로 돌려주어 모델이 다른 출처로 우회하도록 처리

토큰 사용량이 크다

차량용 전략 분석 1건에 입력 토큰 약 49만, 중국 200MP 분석 1건에 약 83만이 사용됐습니다. 긴 기사 원문이 매 턴 다시 전달되기 때문입니다.

→ 다음 개선 과제: 원문 길이 제한, 핵심 기사만 원문 조회

08

결론

이미지센서 사업 동향을 자연어로 요청하면 AI가 스스로 도구를 골라 실제 데이터를 모으고 보고서까지 만드는 에이전트를 만들었습니다.

웹 UI와 CLI에서 요청 → Tool 실행 → 실제 결과 → 보고서가 이어지는 것을 확인했고, 실제로 3건의 분석 보고서와 기사 156건·인사이트 3건이 DB에 쌓였습니다.

LLM은 판단을, Tool은 정확한 처리를 맡기는 구조가 핵심이었습니다. 다음에는 토큰 비용을 줄이고, 공개 RSS 대신 유료 뉴스·시장조사 데이터를 연결해 보고 싶습니다.
